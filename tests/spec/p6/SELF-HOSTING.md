# Separate P6 self-hosting proof

Feature 1 is issue 3 (`inspect`). Feature 2 (`explain`) is not implemented or specified by this bundle. P6 is incomplete until both useful changes have real factory-created PRs, passing exact-head CI, independent baseline-red/candidate-green evidence, and human review/merge.

First complete the exact P5 baseline's P3/P5 live proofs and obtain human merge of the CI bootstrap PR. Build/install version N outside the writable target worktree, pin its executable/source and the external acceptance bundle, and keep both stable throughout the feature run. The product worker receives the approved issue, allowed source scope and frozen tests. Candidate N+1 runs only as a child under verification; it cannot replace its runner or judge.

Before depending on nested CLI acceptance inside the factory verifier, run an isolated learning probe of the native sandbox boundary. The full CLI fixtures launch a Windows job supervisor using PowerShell `Add-Type`, which may be unavailable under the verifier's constrained language mode. Establish a trusted external verifier orchestration path that can execute the frozen real-process tests while preserving worker restrictions and binding its result to the exact candidate and bundle. An in-process TypeScript check followed by manual host-side tests can support a clearly labeled bootstrap change; it does not by itself prove the autonomous P5/P6 path. Do not weaken the worker sandbox or substitute a narrower test and claim full self-hosting. This is an unresolved prerequisite, not a new inspect behavior contract.

The [prepared-fixture feasibility probe](../../../docs/research/p6-verifier.md) now passes for VERIFIED and active-owner baseline fixtures: host preparation, restricted in-process compilation, read-only CLI execution and complete scratch cleanup work without changing protected inputs. The 16-case prepare/assert refactor and actual factory integration are still outstanding. This result does not authorize skipping those steps or claiming P6 acceptance.

For at least one of the two real feature runs, define a concrete product question whose answer is not in the work contract. For example, on the later `explain` issue, leave one bounded presentation choice explicitly reserved to the human rather than inventing uncertainty in the already-frozen inspect output. The real worker must publish the decision, persist waiting, exit, obtain the configured user's concrete answer, and continue in a new process with that recorded resolution. Retain the actual issue/comment and authority record. A scripted fixture or factory-written answer alone cannot satisfy this gate.

Separately exercise deterministic self-hosting with a trusted fake worker that first returns a candidate violating a frozen inspect assertion, then repairs it from measured failure context. Prove failure cannot deliver; only the allowed repair reserves a repair count, total starts remain bounded, and exhaustion stops. Include an attempted change to the external acceptance bundle or running N installation, and prove the protection prevents it and hashes remain unchanged. This deterministic scenario still needs its own executable harness before the P6 gate is claimed; the inspect fixture tests alone do not implement it.

Audit the real run chain: issue, run ID, immutable base, attempts, human decision, candidate tree, measured verification, commit, PR, exact CI head, human review and merge. Record any operator intervention. A manually patched source/state/result does not count as autonomous success. Only after human merge and acceptance may the next binary and verification bundle be promoted for later runs.
